# Proof of Stage

> **The column says zero. The report says eight.**
>
> Proof of Stage finds database records that cannot be true as written, quotes the source document that shows which field is wrong, and leaves the fix to a person. It never edits a record.

Track 2 "The Agent That Can Explain Why" · NCI's public breast-cancer registry (TCGA-BRCA, 1,097 records) · Zetaris · NVIDIA Nemotron · Meterless

**One question, three answers.** How many patients had cancer in the lymph nodes? Asked of our Zetaris layer, on the 663 records where both columns apply:

| Read from | Answer |
|---|---|
| the stage field (N category) | **336** |
| the positive-node count field | **328** |
| the quote-checked reading: where the two disagree, the field the report contradicts is set aside | **333**, and 2 left to a person |

TCGA-E2-A572 has 0 in the count field; its report says "Lymph node status: Positive 8 / 13". The source check passes on all 1,097 records; only a cross-field rule finds the 24 that cannot be true as written.

**How:** a SQL rule in the layer finds the record; Nemotron may only quote the report; a code check confirms the exact words are there; a person decides. Against blind labels from one lay labeller (the builder): the product 18 of 25, Nemotron Super alone 17, level on accuracy. Every model comparison was written down before it ran; the losses are published.

## In detail: the three answers and how they are decided

Live from the semantic layer (`usl demo` step 11, `docs/zetaris-demo.md`):

| Read from | Node-positive |
|---|---|
| the registry's N category column | **336** |
| the registry's positive-node count column | **328** |
| the quote-checked reading (the verdict column, `stage_check.fault_field`): where the two columns disagree, the field the pathology report contradicts is set aside; where they agree, they stand | **333**, and 2 left to a person |

The two columns disagree on 10 of 663 records where both apply, and the basic source-level check (positive nodes never exceed nodes examined) passes on all 1,097: the errors are visible only across fields. One of the 10, TCGA-E2-A572, is recorded with 0 positive nodes; its report says "Lymph node status: Positive 8 / 13". The 333 is the quote-backed reading, not ground truth: the report decides only the 10 disagreements (8 settled, 2 to a person), and those readings were scored against blind labels from one lay labeller (the builder): 8 of the 10 agree; on TCGA-BH-A0BS and TCGA-E2-A1LI the label leaves the decision to a person, and the Ultra second reader also objects to E2-A1LI's reading (`docs/evidence/baseline-m0-results.md`, `docs/evidence/ultra-critic-results.md`). The stored values were first written by earlier NVIDIA-direct reads without receipts; on those 10 records the latest evidence runs (20 steps, each with a Nightshift receipt whose signature was checked at run time against a pinned key) reproduce all 18 stored report values (each with its receipt: `docs/evidence/nightshift-provenance.md`).

**How it decides**
1. **The semantic layer proves the record is impossible.** A SQL rule in the Zetaris USL, over three live sources (the NCI GDC API, a file store, Postgres): the recorded N category and the record's own node count cannot both be true (24 of 1,097, plus 1 missing N the count could fill).
2. **Nemotron may only quote the report.** Lightning reads first with thinking off; Super VL with a 4k thinking budget reads what is still open; Nemotron Parse reads the original scan. Every text call the product makes goes through Nightshift with a signed receipt; Parse goes to NVIDIA direct.
3. **Code checks every quote:** it must be in the report and show the value; otherwise the value is rejected with a reason.
4. **The semantic layer names the field** the report contradicts (node count, N category, or a person decides), and **a person decides**. Every write is append-only.

**Measured, pre-registered where marked** (each number links to its file):
- The verdict names a field for **21 of the 25** queue records (24 impossible + 1 missing N; 8 node count, 13 N category); 4 go to a person ([Results](#results-live-2026-10-22-to-10-24-every-number-has-its-file)).
- **Red team (pre-registered):** Nemotron as a Markovian attacker, 0 wrong accepts in 57 judged attacks ([v3](docs/evidence/adversary-chain-v3-results.md)).
- **Reasoning dial (pre-registered):** thinking off first, then 4k, used 40% fewer tokens than always 4k (measured with Super at the first read; the shipped chain, with Lightning there, was not measured for cost); 0 of 31 cheap closings contradicted ([dial](docs/evidence/dial-sample-results.md)).
- **Model per step (pre-registered):** Lightning took the first read from Super (18 vs 15 of 28 settled; of 38 closings 33 confirmed, 0 contradicted, 5 unconfirmed; a controlled same-session re-run confirmed it settles more (16–17 vs 13–14 of 28 in each of 3 trials, 0 contradicted) but showed it is **not faster** (median 2.17 s vs 1.92 s per read) and uses more tokens, [timing](docs/evidence/r1-timing-results.md), [Lightning](docs/evidence/lightning-r1-results.md)); Ultra lost the case-note seat to Super (8 vs 21 of 25, [Ultra](docs/evidence/ultra-notes-results.md)).
- **An agent reading the layer (pre-registered, 3 probes, 30 calls):** given only the descriptions, Super wrote a query in 19 of 20 calls and all 19 read the raw count column: 14 returned 476, leaving out the 6 patients the verdict corrects; 3 returned 0 because the descriptions did not say counts are stored as "4.0"; 1 was refused by our read guard; the last one, the only query that also read the checked column, included them but filled the 3 cases left to a person back in from the raw count (482, not 479). A pointer to the verdict changed nothing (0 of 5 with it, 0 of 5 without), and neither did the layer's own data-quality rules rendered into the schema as `LOAD USL` returns them: all 10 queries of the third probe, with and without the rules, counted the raw column and returned 476 ([probe 1](docs/evidence/agent-probe-results.md), [probe 2](docs/evidence/agent-probe-2-results.md), [probe 3](docs/evidence/agent-probe-3-results.md)). So the product writes the verdict into the layer and answers the question itself.
- **Nemotron alone vs the product, against blind labels from one lay labeller, the builder (pre-registered):** the product agreed with the label on **18 of 25** cases, Super alone with 4k thinking on 17, Super with thinking off on 9, the count rule alone on 7. On accuracy the product and Super-with-thinking are within one case; what the product adds is a guard-checked quote and an append-only record for every value (Super alone also ran through Nightshift with signed receipts) ([baseline](docs/evidence/baseline-m0-results.md); one lay labeller, a standard close to the product's own logic, both disclosed before scoring).

## Why it matters: agents trust the semantic layer

Agents now read data through semantic layers: the layer tells them what every table and column means, so they can query without ETL. But a semantic layer gives meaning, not truth. The layer describes TCGA-E2-A572's two columns perfectly, and anything counting node-positive patients from the count column leaves this patient out, with nothing in the chain noticing. Proof of Stage puts the missing piece inside the layer itself: a verdict per record (`stage_check.fault_field`) naming which field the source document contradicts, next to the accepted reading and its verbatim quote (`derived_stage`, also in the layer). Anything that reads `stage_check` gets that verdict next to the record, and the layer's own descriptions of the N and count columns (what an agent reads to learn the schema) point to it (`040_descriptions.sql`). We tested whether that is enough (pre-registered, `docs/evidence/agent-probe-results.md`): Nemotron Super, through Nightshift, given only the layer's table and column descriptions and asked "how many patients are node-positive?", wrote a working query 9 of 10 times and used `fault_field` **0 of 10 times**, with or without the pointers. Its answer counted from the count column and left out all 6 patients the report shows node-positive but the count records as 0, E2-A572 among them. A pointer in the description was not enough. A follow-up (pre-registered, `docs/evidence/agent-probe-2-results.md`) put the checked count itself into the layer, beside the raw one (`stage_check.positive_nodes_checked`): the agent read it in 1 of 5 calls; that query did include the 6 patients, but filled the 3 cases left to a person back in from the raw count (482, not 479). So we do not claim agents pick up the verdict on their own: it is for the people and tools that read `stage_check` and the case page. This matches a recent controlled study of agents and data-quality metadata (Besanson, "SARC-DQ: Runtime Data-Quality Gating for Agentic AI", arXiv:2607.26313, 2026): competent agents silently acted on defects carried in metadata about 60% of the time while raising no flags, and a check placed before the action recovered the loss on the signals it covered. In Proof of Stage that check is the person deciding. A design lesson from that one query (not re-tested): the checked count leaves every case for a person empty, the agent read empty as missing data and filled it from the raw count; even counted directly, the checked count gives 331 on the first-screen cohort where the verdict gives 333, because two cases left to a person are node-positive on both registry columns (`usl demo` step 11). Of the 10 records where the columns disagree, the quote-verified report reading settles 8 (6 node-positive patients recorded with 0 positive nodes, 2 node-negative patients recorded N1) and leaves 2 to a person (`usl demo` step 12); 14 more contradictions keep the same yes/no answer but change the N category. `nodes_within_tested` holds on all 1,097 records; only the cross-field rule sees the 24. Scored against blind human labels (one lay labeller), the layer agrees on 8 of those 10; on the other 2 the label leaves the case to a person.

The problem is not medical: a database says X, the source document says Y. Which field is wrong, and can you prove it? Cancer staging on NCI's public data is the worked, measured example; you do not need to know staging to follow it, only that the count and the category disagree and the report settles it.

**Pointing it at other data.** Reused as-is: the record / source-document / rule / verified-reading / verdict pattern, append-only writes, signed receipts, the evidence chain, the red-team chain, the case page. Rebuilt per domain: the consistency rules (SQL in the layer) and the guard's field checkers (ours knows how pathology reports write node counts; dates, amounts and identifiers are simpler). Candidate uses, untested: clinical-trial source data verification (the trial database against patients' source documents, today done by hand), registry and research-dataset audits, claims and forms against their attached documents. Built and measured on breast cancer staging; four pre-registered tries on other data are in [Pointing it at other data](#pointing-it-at-other-data).

## What a judge sees in one case

TCGA-A2-A0CV: the registry says N1a and 4 positive nodes; 4 nodes would be N2a, so both cannot be true. Nemotron reads the report and quotes "(2/18) POSITIVE EXAMINED LYMPH NODES"; the guard confirms the quote and that 2 is the positive count inside it; the semantic layer names **the node-count field**. On the original scan, Nemotron Parse boxes the line "METASTASIS IN TWO OF EIGHTEEN (2/18)". This is the live result; in offline sample mode the same case shows the contradiction and lets you play the reader (no model output is bundled or replayed).

## How it works

| Layer | What it does | Where |
|---|---|---|
| Zetaris USL `stage_audit` | 8 tables over 3 live sources: the NCI GDC REST API (cases, recorded stage, node counts), a file store (paraphrased staging rules, report text, Parse blocks) and Postgres (append-only reader output and review log); 8 custom data-quality rules (one basic source-level rule; `fault_named` / `fault_unresolved` are review queues expressed as rules) + the 13 key rules Zetaris generates from the DDL (11 addressable by name; the two composite primary keys run under their first column's name, which checks the full key, because their listed names need backquotes and our read guard refuses those; `usl demo` also checks their full uniqueness directly); the case page reads only USL tables; its lineage panel comes from `LOAD USL` | `app/usl/`, `app/usl/sql/`, `docs/zetaris-demo.md` |
| Nemotron Super | We request `nvidia/nemotron-3.5-super-vl-120b-a12b`; NVIDIA's API reports it served as `private/nvidia/nemotron-3.5-super-120b-a12b` (its alias, `app/config.py`), and Nightshift's signed receipts name the VL id. Reads the report; returns T, N and the positive-node count, each with ONE verbatim quote; a 4k thinking budget on the deep and scan reads; the first read is Nemotron Lightning with thinking off (next table) | `app/reader/reader.py` |
| The guard (code) | Accepts a value only if its quote is in the report **and shows the value**. For N and T: a matching stage token or label ("pN1a", "N Stage: 1a"); for N, a node count that passes the whole count guard below and implies the N (2 positive → N1); for T, a tumour size in its range after a tumour cue (not a node, margin or specimen size); or the words of a category a number cannot show, not negated and about the right element (micrometastasis; "regional lymph nodes … cannot be assessed", not pM; skin or chest-wall invasion, not just "skin"; in situ without invasion). For a count: the first number of a positive fraction ("2/18"; not a score like "8/9", not "eight of eight … free of carcinoma"), or else the number nearest a positive cue ("positive", "metastatic"), never one with a unit or a grade around it in the report; not below any node fraction the report states; and equal to the total when the report states one with a label ("Number of positive lymph nodes: 4"). Each rule closes a hole a red-team or review found (`docs/evidence/guard-floor.md`). Known limits: a per-specimen count or N when the report states the total neither as a fraction nor with a label; a count above every stated fraction | `app/reader/` |
| Nemotron Parse | Reads the original scanned PDF from the GDC; every text block with its box; stored as the USL table `parse_block` | `app/scans/` |
| `stage_check.fault_field` (USL) | node_count / pathologic_n / review, from the registry, the count rule and the quote-verified reading | `app/usl/sql/055_activate_stage_check.sql` |
| Meterless Markovian engine | The official reference, vendored unmodified (`vendor/meterless-markovian`, conformance 8/8); our Node sidecar wraps one method at runtime only to record which carryover level the engine chose. **Two chains.** (1) The evidence chain, one per case: each chunk is a step (the first read, thinking off → the deep read, 4k → the scan read); our code writes the carryover `{need, consulted, ledger}`, which picks the next step and ends the chain when no field is open; the model reads the document beside the engine and never sees the carryover (so no reading can anchor the next), which makes the engine's savings 0 by construction, and we claim none. (2) **The red-team chain**, where Super is the generator: each step it sees the engine's `[CARRYOVER STATE]` (a code-written ledger of its earlier attacks and the guard's verdicts) and proposes a new attack; pre-registered, 3 cases × 20 steps (`docs/evidence/adversary-chain-results.md`) | `app/engine/` |
| Meterless Nightshift | **The provider for every text call the product makes** (a few earlier measurements and `doctor`'s comparison call went to NVIDIA directly; each says so in its row). The evidence chain's text steps (thinking off, a 4k thinking budget) and the case note go through Nightshift (since 1.2.3 it forwards the thinking switch and the budget; `docs/evidence/nightshift-limits.md` §6), with the step's model required in the signed receipt (Lightning for the first read, Super VL elsewhere; on 1.2.1 a model id alone did not always pin a lane; on 1.2.3 it does: 166 of 166 and 28 of 28 calls were served as requested), the receipt's Ed25519 signature verified against a pinned key (`NS_RECEIPT_PUBKEY`; Nightshift publishes no key, so we pinned the key of the first verified receipt and every later one must match), cached answers refused, and `python -m app.cli doctor` printing the signature state and the signer's key fingerprint. NVIDIA direct stays as a documented fallback (`run --provider nvidia`); only Nemotron Parse on the scan images goes direct, because Nightshift offers no lane for it | `app/engine/rungs.py`, `app/notes/note.py`, `app/providers/nightshift.py`, `app/providers/receipts.py` |
| Case page | One case at a time: the headline, the USL steps, the highlighted quote, the guard checks, rejected answers, the Ultra second reader's objections (read-only, from its logged run), the case note with its Nightshift receipt, decisions written back to Zetaris, "Try to fool it" | `app/web/` |

**What is unique in how we used them:** the semantic layer does the proving and the model only quotes: Nemotron never decides a record, the SQL rule finds it, code checks the quote, the layer names the field and a person decides. Nightshift is used as a verifiable provider (signed, pinned, cache refused), not only a router. The Markovian engine runs an evidence chain whose model never sees the carryover, plus a red-team chain against our own guard. And each model choice was pre-registered and measured, including the ones that lost.

**Exceptions, stated:** Nemotron Parse and Super VL reading page images go to NVIDIA direct, because Nightshift has no Parse lane and 1.2.3 refuses pinned image requests with `no_vision_model`: its vision gate filters the automatic pool before the pin is applied, and every NVIDIA vision row is experimental, so never in that pool. The same requests worked on 1.2.1; reported to Meterless (`docs/evidence/nightshift-limits.md`, `logs/capability-retest-2026-10-24.jsonl`).

Nightshift setup we used (1.2.3, Windows): Adaptive compute, Self-refine, Answer fusion, Reasoning scaffold, Optimistic streaming and Tier-split **off** (so an answer is one model's own text); the cloud Lightning lane moved from Race to Judge. **Nightshift 1.2.3 switches Super VL off by default** (Meterless measured it unstable: 31 of 94 hosted calls failed); we opted back in with its documented flag `NVIDIA_SUPER_VL = "true"` (a key in the runtime's `state/engine-kv.json`, set while Nightshift is closed), so every read stays on the model all our measurements used. Without it every pinned call is refused with Nightshift's own message naming the flag.

## Cost, in one place

- **The reasoning dial:** on 28 records whose registry fields agree, the evidence chain (Super at the first read, before Lightning took that seat; the shipped chain was not measured for cost) used **40% fewer completion tokens** (56,160 vs 93,419) and 20% less time than reading every record at a 4k budget, and the cheap read was contradicted 0 times in 31 (`docs/evidence/dial-sample-results.md`). On the review queue it costs more than always-4k, by construction (a contradiction case always needs the deep read).
- **The thinking setting itself:** off answers in about 19 completion tokens and 0.6 s, a 4k budget in about 1,000 tokens; on 42 reports (84 fields), 4k got 30 both-right against 26 with thinking off, and matched unlimited thinking item for item (`docs/evidence/thinking-budget.md`).
- **Markovian carryover (the red-team chain):** 62,806 measured prompt tokens; 7,243 more (about 10%) would have been sent by a transcript that resends every attack (estimated, chars/4) (`docs/evidence/adversary-chain-results.md`). The evidence chain saves nothing by design (its model never reads the carryover).

What held: in every database the rule finds records that cannot be true as written, and they sit in the rows typed in from paper. What did not: the reading, as built. The misses taught us two things. ## Nightshift: what 1.2.1 could not do, and what 1.2.3 fixed

We integrated Nightshift first and measured where it could not do the job (`docs/evidence/nightshift-limits.md`): on 1.2.1 it replaced the client's thinking switch with the model's default (thinking on), forwarded no `reasoning_budget`, and cut cloud calls at 45 s, so the evidence chain's two text steps and the red-team generator had to go to NVIDIA directly. We reported it to Meterless with the code lines (`providers.js`, `nvidiaThinkingBody`); Meterless confirmed the fix in a private reply. The cloud timeout is already configurable in 1.2.3: the `cloudTtfbMs` setting (5–300 s, 45 s by default) or per request with the `meterless-ttfb-ms` header; it limits the time to the first token, not the whole call. 1.2.3's code already says "a caller that names a kwarg gets exactly that kwarg (2026-10-22: it used to be replaced by the row default)".

Measured on 1.2.3, Super VL pinned, the reader prompt on full reports (`logs/nightshift-123-super-vl-2026-10-23.txt`): thinking off 1.9–8.7 s; a 4k budget 74–92 s and not cut (the limit is time to the first token); every answer Super VL, signed by the pinned key, none cached. Nightshift's usage reports no reasoning-token count, so through Nightshift the budget shows only as completion tokens of about the budget plus the answer (4,174 and 4,215 at 4,000); the to-the-token measurement is the one made directly (`docs/evidence/thinking-budget.md`). One direct read of the same report took 40.7 s, at a different time and load, so we draw no speed comparison.

Still direct: Nemotron Parse on the scan images (no Nightshift lane for Parse); Super VL reading page images (on 1.2.3 pinned image requests are refused with `no_vision_model`, because the vision gate filters the automatic pool before the pin and every NVIDIA vision row is experimental; the same requests worked on 1.2.1; reported to Meterless, `logs/capability-retest-2026-10-24.jsonl`); and the finished red-team run v2, pre-registered on NVIDIA direct because 1.2.1 could not carry its budget (`docs/evidence/adversary-chain-results.md`).

## Reflection on the Zetaris USL

**Built** (`app/usl/sql/`, run in order by `usl setup`): identified 3 kinds of source (the NCI GDC REST API; file-store CSVs of paraphrased rules, report text and Parse blocks; our own Postgres results), onboarded each (`020–022` REST, `010–016` file store, `002–005` Postgres), queried each, compiled one USL `stage_audit` (8 tables, primary and foreign keys, 88 table and column descriptions in `040_descriptions.sql`), queried it (the case page reads only USL tables; `usl demo` is a timed query pack) and added data-quality rules (one basic source-level rule, `nodes_within_tested`, plus 7 custom rules and the 13 key rules Zetaris generates from the DDL).

**How it saved time.** What we measured: the whole cross-source audit, 21 rule results over 1,097 cases from three source types, runs with one command in 44.8 s (`usl dq`, `logs/usl-dq-2026-10-23.txt`), and the reproducible demo pack in about 39 s (`docs/zetaris-demo.md`). We did not time a manual or hand-coded alternative, so we claim no "hours saved" number. Lines of code, counted (non-blank): the **rule logic is about the same size either way**: our 8 custom DQ rules are 32 lines of USL SQL (`060–067`), and the Python mirror we keep for offline tests (`app/usl/dq.py`: 5 of those rules plus the verdict, helpers included) is 123. What the USL removed is the code around the logic: that Python only checks one row already in memory, while in the USL one 7-line statement (`021`) onboards the GDC API (a hand-written fetch of the same fields was 26 lines of Python in an earlier spike outside this repo), the join across the three sources is SQL in place, `RUN DQ` runs every rule over every row and reports the violations, and the 13 key rules are generated from the DDL (0 lines). What we did not have to build: an ETL step (the verdict `stage_check.fault_field` is one SQL CASE over the GDC API, the CSVs and Postgres, joined in place); a reload step (a value the reader appends to Postgres is in the next USL query); a lineage view (the page's lineage panel comes from `LOAD USL`); our own key checks (the 13 key rules come from the DDL).

**How it can help in our work.** The layer is a pattern, not a cancer tool: a record table, a source-document table, a rule table, the model's verified readings and a verdict, with every write append-only. Only the rule table is about staging. The same shape fits other "does the record match its source document" audits (trial source-data checks, claims against clinical notes, invoices against an ERP); we have not tested those.

**How to improve it** (each one observed while building; build journal ids in brackets):
1. A schema change clears the live layer: `UPDATE USL … AS` exists but, as Zetaris's reference documents, clears the activation (the next SELECT says "is not activated"), as REMOVE USL + COMPILE does. Keeping the previous activation live until the new one is activated would avoid the gap (M17; retest in `logs/zetaris-retest-2026-10-24.jsonl`).
2. The generic "Invalid DDL statement" error does not name the offending token. We hit it with a bare `varchar` (no length) and with names that look reserved (columns `text` and `kind`, a table `doc`); an error naming the token would save a search (M17; our earlier note blamed `double`, which a retest shows compiles: `logs/zetaris-retest-2026-10-24.jsonl`).
3. A file-store table keeps its first schema when the CSV header changes; we had to drop and re-register it (M17).
4. `'O''Brien'` returns `OBrien`, not `O'Brien`: Spark SQL reads adjacent literals as one concatenated string and escapes with a backslash, which works. That is Spark's semantics, not a bug, but a line in the docs would save a search for anyone coming from standard SQL (M14).
5. We only INSERT into the Postgres datasource (append-only by design); we did not test UPDATE or DELETE through it, and we did not find in the reference whether a registered datasource takes them. A line in the docs would help.
6. A REST round trip takes about 0.6 s (`SELECT 1`, 10 calls, median 0.555 s, `logs/zetaris-retest-2026-10-24.jsonl`); a page that runs a dozen queries pays that each time, so a read-only batch endpoint (several statements per call) would make pages faster.
7. What reaches an agent: `LOAD USL` carries all 8 custom rules in the table-level `dqAnnotations` (name, expression, CTE), because they are table rules (`REGISTER DQ … TABLE`); the column-level arrays are empty, and `acAnnotations` is empty because we set no access policies. A third pre-registered probe rendered those rules into the agent's schema exactly as `LOAD USL` returns them: 0 of 5 calls used the verdict, all 10 counted the raw column (`docs/evidence/agent-probe-3-results.md`). Run counts (how many records fail) beside each rule would make them more useful to an agent. (Correction 2026-10-24: this item used to say the rules do not reach `LOAD USL`; we had looked only at the column-level arrays.)
8. What helped: the NOT NULL mismatch error suggested the exact COALESCE fix (M17).
9. Least privilege for an agent needs one more step than expected (probe 5, `docs/evidence/agent-probe-5-results.md`). A role granted only a schema-store view over `stage_check` was refused the view: the reader also needs access to the view's source table, and that table holds the raw count we wanted to keep from the agent. A snapshot table in its own Lightning database worked, but it is not live. A view that grants its own columns, or column-level policies on USL tables, would let an agent account read the checked values live and nothing else. What worked well: Zetaris's own refusal ("User … does not have access to USL …") is clear and names the object.
10. In a second USL (`attest_audit`), a column named `run` gave the same unnamed "Invalid DDL statement" as item 2; `run_tag` compiled.

| Errors | the server's message first, then its `fix[]`; a 429 retries after 2, 4 and 8 s | yes | `app/providers/nightshift.py` |
| Local-only | local-only work never reaches a cloud provider | yes: Jobs API with `privacy: local-only`, every resolved lane checked | `nightshift.local_job` |
| L2+ | attachments, media, transcription, 3D, Quick Connect | not used (a text-only audit) | |

One deliberate difference: the contract sends `meterless-scope: user` on chat; we send a unique `meterless-scope` per call, so the runtime's memory never mixes one case's report into another's answer (we saw the runtime inject memories into requests early on). Every receipt is checked: the winning model, `egress`, `context_sources` (only `messages`), the cache status and the Ed25519 signature against the pinned key.

## Limits (honest)

- Hosted Nemotron Parse 2.0 returned an empty document on 10-19 and 10-22 (even on NVIDIA's own example); on 10-24 it worked in a retest, then returned 12 of 19 pages empty in the pre-registered comparison (`docs/evidence/parse-bench-results.md`). Parse v1 stays the measured scan reader.
- Two of six scan boxes missed on a sparse one-page form; the page then shows no box and a person decides.
- The checks cover N vs the node count in the 6th/7th editions; T, M and stage groups are not audited yet.
- The evidence chain reads the report text from the local corpus copy and the scan from the local Parse cache (the same text the USL serves); moving those reads onto the USL tables is planned.
- Append-only storage: the first value written for (case, method, field) stays, even if a later read is better; later reads are logged as `kept-earlier`.
- "Impossible" means impossible under our paraphrased count rules (data/README.md), not the AJCC manual itself; edition windows overlap (6th 2002–2010, 7th 2009–2018).
- The GDC REST table is cached (refreshed by `usl setup`); report text and scans are not committed (licences and size).
- The reader's known traps, from the second census (7 of 18 hits fell): it can take one part's node count for the total when a sentinel node was submitted separately (5), and in a bilateral case it can read the other breast (2). Its quote is real in every case; the value it drew from it was not the record's.
- Research data, not for clinical use.
